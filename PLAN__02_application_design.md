## Purpose and recommended starting point

Build a repeatable way to describe when a researcher-like browsing session encounters access interference for an existing Cloudflare configuration. Purpose: to gather objective data for when we work with Central IT to make Cloudflare configuration changes. Objective: for a given Cloudflare configuration, for us to be able to supply the date, urls-checked, and multiple access-frequency data-points -- to assess the real-world implications of a given configuration.

Use a Python command-line app with Playwright and one visible Chromium browser. **In the first version, each invocation of the app runs one trial:** one collection identifier, one workflow, and one set of timing targets. Start each trial with a new browser session that does not reuse cookies or cached files from earlier trials. All tabs in a trial share that session; Playwright calls it a `BrowserContext`. Both workflows are available in the first version, and each trial uses the selected workflow. Both open the first collection listing page with 50 items per page requested, select every other item thumbnail up to 20 items, and follow these distinct sequences:

1. **Workflow 1 (`tabs`): Open all selected items in separate tabs first; then inspect them.** Stay on the collection overview while opening the selected thumbnail links rapidly, about one second apart, each in its own new tab. Only after the selected item tabs have been opened, switch to the first item tab and spend about five seconds scrolling down its page in sections, pausing as though skimming each newly revealed area. Then inspect each remaining item tab in opening order in the same way.
2. **Workflow 2 (`return`): Inspect each item before opening the next, using one tab throughout.** From the collection overview, open one selected thumbnail in the current tab and spend about five seconds scrolling and skimming in the same way. Follow its back-to-collection link in the same tab. Scroll the overview if needed, then open the next selected thumbnail and repeat the open/inspect/return sequence.

The first workflow models the reported case of a researcher opening numerous item tabs before being blocked. Run both workflows in separate trials. Record requests from the first collection visit. Stop further browsing at the first relevant challenge, denial, error, or time limit. Save JSON records and a readable Markdown report locally. When a different public IP address is needed between trials, the person running them prepares that change outside the CLI app using separately managed tools. The public IP address is the address BDR sees for the browser's connection.

Vary the timing using a saved starting number, called a random seed, so the app can reproduce the same planned sequence. An approximate average is sufficient. The workflows are requested behavior; the detailed settings and coding choices below remain proposals.

A block observed in one trial does not establish a request limit that applies in every situation. Cloudflare can consider information sent with requests, the browser session, and other browser behavior. Its rate-limiting rules can group and count requests using more than an IP address. Small timing variations approximate a browsing rhythm but do not make an automated browser equivalent to a person using a browser. [Cloudflare bot scores](https://developers.cloudflare.com/bots/concepts/bot-score/), [rate-limiting parameters](https://developers.cloudflare.com/waf/rate-limiting-rules/parameters/).

Each report must include a short **Known unknowns and evidence limits** section. List relevant uncertainties identified for the run, such as the public IP address's recent use or location, unconfirmed Cloudflare behavior, and differences between automated and manual tab use. Keep the list specific; it need not cover every imaginable concern.

## Trial procedure and timing

### One trial

1. Record the workflow, timing settings, selected thumbnails, the user's label and notes for the current Cloudflare settings, and when those settings took effect. Also record the internet connection being used, including any VPN, proxy, or Tor setup, and the public IP address BDR sees. Keep these conditions unchanged throughout the trial. Start with a public IP address expected to have access to BDR; record any known recent use of that address and how long it has been since a previous block.
2. Start a new browser session, keeping its cookies and cached files throughout the trial and sharing them across the trial's tabs. Begin recording network activity from every tab before the first BDR request. Use the collection visit as the initial access check, without making extra BDR requests beforehand.
3. Visit the collection overview with `?page=1&per_page=50` and choose a limited number of every-other-item thumbnail links in their displayed order. Carry out the selected workflow below. Record gathering links, opening items, reviewing tabs, returning to the overview, any adjustments to the items-per-page setting, and scrolling as separate actions, while keeping all resulting network activity in the record.
4. Keep the chosen timing targets unchanged. Stop further actions on interference, the time limit, interruption, or an error that prevents reliable measurement, and save the results collected so far. Reaching the item limit or the end of the selection prevents more item openings but allows the remaining review/return steps to finish within the time limit. Otherwise, finish when the workflow is complete.
5. Let the app save the results and close all trial tabs. The person running trials then prepares any needed public IP address change outside the app before starting another invocation. A different public IP address or workflow requires a new trial and identifier. A challenge on the first collection visit means initial access failed; it does not establish that this trial caused the block.

An initial successful collection visit shows that access worked at that moment. It does not prove that Cloudflare has no earlier requests counted for that address or that the address has no relevant history. Gathering thumbnail links may itself cause interference, so those requests must remain in the report.

### Timing definition

Keep **time between item openings** separate from **time spent viewing an item**. Measure an opening interval from the start of one item-opening action to the start of the next, and record the related page-request start times separately. Viewing time begins when the tab is selected for review and the expected item content is ready; waiting for that content is additional time. The viewing duration covers the whole item-viewing step, including scrolling and pauses over newly revealed areas; it is not a separate duration for each section of the page.

| Workflow | Proposed starting timing | What determines when the next item opens |
| --- | --- | --- |
| `tabs` — open tabs, then review | Open an item tab about every `1.0` second, varying by up to `0.1` second either way. After opening the selection, spend about `5.0` seconds per tab scrolling down in sections and pausing to skim, varying the total viewing duration by up to `0.5` second. | The planned opening time and availability of the next collection thumbnail. Earlier tabs may still be loading. Item-page scrolling and viewing begin after the opening stage. |
| `return` — item and overview in one tab | Spend about `5.0` seconds per item scrolling and skimming in the same way, varying the total viewing duration by up to `0.5` second. Then follow its back-to-collection link and find the next thumbnail. | Loading the item, viewing it, finding and following the return link, waiting for the overview, and any overview scrolling. Item-page scrolling is included in viewing time; the other steps add time. The actual time between openings will usually exceed five seconds. |

Use the following item-viewing sequence in both workflows:

1. Begin at the top of the item page once its expected content is ready. Pause over the initially visible area as though skimming it.
2. Scroll down by about 80% of the browser's visible page height, leaving some overlap with the previous area. Pause over the newly revealed area before scrolling again. As an initial proposal, use one-second pauses, shortening the final pause to the viewing time remaining. Keep this scroll distance and pause length fixed across a trial and record them with the timing settings.
3. Continue until the planned viewing time expires or the page cannot scroll farther down. If the bottom is reached early, spend the remaining viewing time there. If the page is longer, end viewing when the time expires and record that the bottom was not reached. A viewing duration shorter than one pause simply shows the initial area without scrolling. Do not rush through the remaining page or extend viewing to reach the bottom, including when more content appears during scrolling.

Scroll the item page itself; operating controls inside an image or document viewer remains outside the first version. Record the start and end of each pause, each scroll's requested distance and observed position before/after, and whether the bottom was reached. Record content or requests triggered by scrolling, including content that was still loading when viewing ended. Keep observing requests from every tab and stop further actions if interference or the trial time limit occurs during a scroll or pause. Collection-overview scrolling remains a separate action used to find thumbnails. In `return`, any scrolling needed to find the back-to-collection link after viewing belongs to the return step and adds to the time before the next item opens.

For each timing target `T` and allowed variation `J`, independently choose a value between `T - J` and `T + J`, with all values in that range equally likely. Use a recorded integer seed and generate values in the same order so they can be reproduced. Require finite values with `T > 0` and `0 <= J < T`. For `T=5` and `J=0.5`, the expected average is five seconds; an individual trial will usually differ slightly. Record the planned opening and viewing times separately from actual times. Do not change later timings to force an exact average.

Use an elapsed-time clock that is unaffected by changes to the computer's date and time; in Python this is a monotonic clock. Use it for durations and request-count calculations. Record dates and times in local Eastern time, interpreting “local-EST” as `America/New_York`: EST in winter and EDT during daylight saving time. Include the numeric timezone offset and name in JSON, event records, reports, and the time Cloudflare settings took effect. Use Python's `zoneinfo` support for this conversion. [Python timezone support](https://docs.python.org/3.12/library/zoneinfo.html).

In `tabs`, calculate the next opening time from the previous actual opening start. Perform one deliberate action at a time while allowing tab loads and requests to overlap naturally. Do not wait for the previous item to finish loading or be viewed. Keep the functions that handle browser notifications brief, track tabs still being opened and their time limits, and avoid waiting for each new tab's first response before opening the next. If an action, scrolling, or browser work delays an opening, record the delay and continue from the actual opening time. Do not speed up later openings to catch up. In `return`, wait for the required page and complete its viewing/return steps before the next thumbnail click. Report actual opening intervals and viewing durations separately, with averages and ranges.

A page is ready when its expected collection or item content is available for review within the allowed wait. Record when content becomes ready in a background tab separately from when that tab is selected for review. If content loads only after switching to the tab, allow a separate timed wait for it and record that wait. Check for failed page openings and recognizable challenges or denials before a tab's review turn. Use checks for the expected page elements rather than assuming that a fixed wait or Playwright's `networkidle` condition proves success. During pacing and viewing, use short Playwright waits and brief checks that allow browser notifications from all tabs to be handled. Check all pending page-opening time limits and whether the whole trial must stop; a slow tab must not prevent observation of the others. [Page API](https://playwright.dev/python/docs/api/class-page), [processing browser notifications](https://playwright.dev/python/docs/library#timesleep-leads-to-outdated-state).

### Comparing runs

Start the app separately for each trial in the first version. Keep common settings in `../.env` and change only the values being compared, using that file or command-line options. Repeating the same command with the same settings runs another trial at the same timing targets. Gathering multiple frequency data points therefore requires multiple invocations.

Run both workflows under recorded Cloudflare settings in separate trials. For `tabs`, vary the time between openings while initially keeping viewing time unchanged; for `return`, vary viewing time and measure the resulting time between openings. The 30-, 60-, 120-, and 300-second reporting periods describe requests within a trial; they do not replace trials at different browsing paces. Where possible, keep the collection, listing page and items-per-page setting, displayed order, starting thumbnail, item limit, browser version, browser display size, item-page scroll distance and pause length, cache settings, random seed, link-gathering limits, and type of internet connection the same. Record differences in selected URLs, gathering links, returns, adjustments to the items-per-page setting, or scrolling, including how far each item page was viewed. Longer viewing times can allow more scrolling and trigger additional requests; include that difference when interpreting comparisons. Group results by workflow and timing settings: the same viewing duration does not make the two workflows generate the same activity. Repeat a useful set of conditions, ideally three times initially, and report the individual results and their range. This is a practical comparison, not a statistical guarantee.

Keep trials with no interference alongside challenged or denied trials, showing their duration and activity. Keep incomplete or inconclusive trials with an explanation of their limitations. Together these provide evidence about the current Cloudflare settings for discussion with Central IT. After Central IT changes settings, use a new label and record when the change took effect. Compare the same paces and other recorded conditions, allowing time for a previous block to expire or using another recorded public IP address. A changed address is itself a changed condition; do not combine unlike internet connections into a single claimed request limit. A short manually operated browser session can later help assess how closely the app's actions resemble researcher behavior.

## Application design

One command runs one trial: it opens the collection, selects thumbnail links in the browser, carries out the selected workflow, saves that trial's results, closes the browser session, and exits. Another trial starts with another invocation of the app. Use a few small Python files for settings, browser actions, timing, and results. Collection browsing and item access share one browser session and internet connection, keeping the app small and easy to watch.

The CLI uses an internet connection prepared before it starts and records the connection description and public IP address supplied by the person running the trial. It can also pass the address of an already configured proxy to Playwright and use it unchanged for the trial. Setting up or controlling VPN, proxy, or Tor services, requesting another IP address, and independently checking which public IP address a connection presents belong to the separate investigation and implementation outside this plan.

Gathering collection links makes requests during each run, and changes to the listing can change what the browser does. The rules used to find thumbnail and return links may need updating when Studio changes. Save the selected list in each run's results for comparison. The app performs one sequence of browsing actions while the browser can load several tabs at once.

Suggested file responsibilities:

- `main.py`: read command-line options and call the other functions.
- `lib/config.py`: choose and validate settings from the command line, environment, and `../.env`; save the chosen settings without secrets.
- `lib/browser_flow.py`: find the collection page, select thumbnails, carry out both workflows, track tabs, and check when pages are ready.
- `lib/measurement.py`: generate repeatable timing values, classify observations, and count requests over the specified periods.
- `lib/results.py`: save events as they happen and write summaries under `../runs/<trial-id>/`, including results from interrupted runs.

Use the Python version specified in the repository and run it with `uv`. Add Playwright and its Chromium browser during implementation; keep `python-dotenv`. Review any inherited packages that the app does not need. Browser requests belong to Playwright; any separately written HTTP calls must use `httpx2`, as the repository requires. The planned browsing does not need a separate HTTP client. Start with Playwright's synchronous Python API: the main loop takes the next action while continuing to process notifications from all tabs. Verify that opening tabs and checking page content preserve the requested pace before trials against BDR. [Playwright pages](https://playwright.dev/python/docs/pages).

## Collection access and browser behavior

Accept a Studio collection PID such as `bdr:nz9qn2kb` and construct its overview URL with `page=1` and `per_page=50`. For the maintainer's example, the first collection visit should use [the explicit 50-item listing](https://repository.library.brown.edu/studio/collections/bdr:nz9qn2kb/?page=1&per_page=50). The maintainer reported a default of 20 items per page for the previous example collection. That provides only 10 every-other-item choices; requesting 50 leaves enough room to select 20 when enough eligible items exist.

Build the explicit URL before making the first BDR request. Start measurement with that visit, without first loading the default 20-item listing. Keep page 1 and the 50-item setting fixed in the first version, even when a trial requests fewer than 20 item openings. All requests caused by loading that larger overview belong to the trial, including requests for thumbnails that are not selected for opening.

Before implementation is complete, verify in the browser that the URL produces page 1 with the 50-item setting selected, how to find the required links, and whether those listing settings survive item visits and returns. Check the actual listing settings, not just the requested URL; a collection with fewer than 50 items can still correctly use the 50-item setting. If the requested listing cannot be established, record the problem and end the trial as unable to complete the intended workflow. Confirm any additional identifier forms separately: Brown's examples use collection API identifiers such as `403`, which should not be substituted for the supplied Studio PID. [Brown collection API examples](https://github.com/Brown-University-Library/bdr_api_documentation/wiki/Collection-API-examples).

### Shared thumbnail selection

Use the same selection procedure for both workflows. Read public item-thumbnail links in displayed order on the overview. Remove repeated links to the same item while preserving order, and record the sort order and filters in use. Select positions 1, 3, 5, and so on by default; a starting-position setting of 2 selects positions 2, 4, 6, and so on. Selecting 20 items requires eligible links through position 39 for the first pattern or position 40 for the second. Record the positions and URLs, and limit the selection to 20 items by default even if the 50-item listing offers more every-other-item choices. The same listing settings, overview order, starting position, and limit must produce the same selected items for both workflows.

For the first version, stay on overview page 1 with 50 items per page requested. Moving to additional listing pages and opening collections within collections are later work. Reading links already present on the page does not require another page visit. On the overview, scroll only as needed to reveal or click thumbnails; item pages use the separate sequence of scrolls and pauses under [Timing definition](#timing-definition). If overview scrolling reveals additional links, use the same limited link-gathering procedure for both workflows and count any resulting requests. Stop gathering links at the time or scroll limit, or when enough candidates are available to select the required every-other-item thumbnails. Record whether the available links were all examined or a limit stopped the search. Explain empty listings, listings containing only other collections, and shorter listings. Use fewer items if necessary, without repeating items or changing the selection pattern to fill the quota.

Save the requested and final overview URLs, requested and observed listing page and items-per-page setting, displayed and selected item order, selection settings, link-gathering actions and duration, and available item count. Match each later click to its selected item, including after checking or restoring the listing settings on a return. If the expected listing cannot be restored or a selected link remains missing, record the problem and end the trial as unable to complete the intended workflow. Keep the original selected items; do not replace them with a new selection after returning. Show differences in selected URLs between trials in the comparison report.

### Workflow 1: Open separate tabs, then review them

1. Open collection overview page 1 with `per_page=50` and choose the items using the shared selection procedure.
2. From the overview, open each selected thumbnail link in its own tab, aiming to start about one second apart with the configured variation. Keep the overview and all item tabs in the same browser session; the default limit allows at most 21 intended tabs. Continue working from the overview while opening the selection, scrolling as needed.
3. After opening the selection, switch to the item tabs in opening order. Once an item is ready for review, spend about five seconds scrolling down its page in sections and pausing to skim, using the sequence under [Timing definition](#timing-definition) and the configured variation in total viewing time. Keep all tabs open through this stage. Record tab switches, when content becomes ready, viewing start/end, scrolls and pauses, and additional requests. Switching to an already-open tab or scrolling it is not another item-opening attempt.
4. End after reviewing the last selected tab, save the report, and close the browser session. Interference, an error, or the time limit ends the trial earlier, even if some tabs have not yet been reviewed.

Reproduce the researcher's “open link in new tab” behavior. Record the method used, verify the destination and referring-page information sent with the request, and check whether the overview stays selected. Do not silently replace thumbnail clicks with direct URL visits.

The implementation temporarily sets the actual thumbnail link's `target` to `_blank`, clicks it with the left mouse button, and restores the original target. It leaves the link's URL unchanged and does not wait for the new tab's response before continuing the opening schedule. This captures initial item requests that visible Chromium missed with middle-click or modifier-click in local checks. The browser's cache remains enabled. Tests with both visible and hidden browsers compare the recorded document requests against the local server's received requests, including delayed responses and redirects.

Match selected items to tabs through their observed requests, with an exact page-URL match as a fallback when request notifications are missing. A loaded item can still be viewed in that case, but the report must identify missing document-response evidence and treat request counts as lower bounds. Do not manufacture missing request events or mistake a missing notification for proof that the page failed to load.

Item readiness requires a visible heading and main content, with an expected item-content section present. Studio also includes a heading in its hidden Feedback dialog, so the check must allow multiple headings and ignore hidden ones. Local test pages include that dialog structure.

Keep the review stage even if an early check finds no extra requests while switching tabs or viewing them; that observation is useful evidence. Do not reload tabs just to create requests. Playwright documents that its pages behave as active pages, so do not assume it reproduces how an ordinary browser slows or changes activity in unselected tabs. Check switching and loading behavior using a small local test website and describe any remaining difference in the report. [Playwright multiple pages](https://playwright.dev/python/docs/pages#multiple-pages), [switching tabs](https://playwright.dev/python/docs/api/class-page#page-bring-to-front).

### Workflow 2: Open an item and return to the overview

1. Open collection overview page 1 with `per_page=50` and choose the items using the same shared selection procedure.
2. Click the first selected thumbnail in the same tab. Wait for the expected item content, then spend about five seconds scrolling down its page in sections and pausing to skim, using the same sequence under [Timing definition](#timing-definition) and the configured variation in total viewing time.
3. Find and click the page's back-to-collection link, scrolling to it if needed. This begins the return step after the item-viewing time ends. Wait for the overview and check that the expected collection, page 1, 50-item setting, sort order, and filters remain in use. If the return has reset the items-per-page setting to 20, use the overview's actual page-size control to select 50 again and wait for the listing. Verify the expected listing and scroll if needed to find the next originally selected item.
4. Repeat the open/view/return cycle for the remaining selected items, up to 20 by default. After viewing the final item and returning to the overview, end and save the trial. Interference, an error, or the time limit ends it earlier.

After the initial collection visit, use the page's actual overview and thumbnail links. Browser-history Back and direct URL visits do not reproduce the item-opening and return steps. Record requests caused by returning or scrolling, without forcing reloads or adding to the request count when the browser uses already-saved content. If the return link is unavailable, report that the workflow cannot be completed. Leave out the upcoming image “next-page” feature, downloads, searches, and further interaction with item viewers.

Restore a lost 50-item setting through the page's control after following the return link; do not rewrite that link or replace it with a direct visit to the saved overview URL. Make one restoration attempt per return when needed. Record the adjustment, its wait, and its resulting requests as part of the return step, including the initial return to a 20-item listing. These actions add to the actual interval before the next item opens. If the control is unavailable or it cannot restore the expected listing, record the problem and stop. Restoration obeys the same time limits and interference-stopping rules as other browsing actions.

Keep normal JavaScript, images, stylesheets, cookies, and caching enabled in both workflows. Do not block supporting files to speed up the trial or change requests in ways that affect caching. Record naturally overlapping requests across all tabs. Record whether the browser is visible, its content display size, language/region settings, browser version, the use of a new session, and any deliberate changes to non-secret request headers or browser settings. Keep those settings fixed within a trial. Initially use normal browser defaults without personal profiles, attempts to disguise browser identity, or automated challenge solving.

## Recognizing interference and counting requests

### Describe the evidence before stating a cause

| Observation | Result and initial behavior |
| --- | --- |
| Expected Studio content is visible, with no relevant interference evidence | Record successful access. A status of 200 alone is insufficient. |
| Response contains `cf-mitigated: challenge` | Record a confirmed Cloudflare challenge and stop further page openings. A challenge does not necessarily mean a lasting block. |
| An identifiable denial page prevents access | Record the evidence and apparent source. Treat Cloudflare as a suspected cause until the evidence or Central IT confirms it. |
| HTTP 403 or 429 without decisive Cloudflare evidence | Record denied access or a “too many requests” response, with the source unknown. Neither status alone proves Cloudflare caused it. |
| Page timeout; failure to look up a website address (DNS), establish a secure connection (TLS), or connect through the proxy; server error (HTTP 5xx); unexpected page; or missing expected content | Record the specific network, application, or unknown error. End the trial without drawing a conclusion about what browsing rate triggers bot protection. |

Cloudflare documents `cf-mitigated: challenge` for its Challenge Pages. A `cf-ray` header provides a request identifier that can help Central IT find the request in Cloudflare's records; its presence alone does not mean Cloudflare blocked it. Save the HTTP status, the limited set of non-secret response headers chosen for recording, final URL, page title, and a brief explanation of the observed result. [Challenge response detection](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/), [Cloudflare Ray IDs](https://developers.cloudflare.com/fundamentals/reference/cloudflare-ray-id/).

Record responses for the main pages and their supporting files or data across the whole browser session, including unselected tabs, the overview, returns, and review periods. A challenged image or data request can disrupt an item even if its main HTML page loaded. Initially, stop on a challenge or denial from any BDR hostname included in the trial, and record whether it affected a page, data request, or supporting file, plus the tab and workflow step. A denied supporting request does not by itself prove the whole page was unusable. Record problems with other websites separately. Decide which BDR hostnames to include before trials; supporting files may use a different hostname from Studio.

Start listening for requests, responses, and failures from the whole browser session before opening the collection. Track each new tab and the action that opened it. A new tab's first request can arrive before Playwright provides its `Page` object, so listening only after that object becomes available can miss a request. Keep requests that cannot yet be linked to a tab, add the tab ID when available, and count each request only once. [Playwright request notifications](https://playwright.dev/python/docs/api/class-browsercontext#browser-context-on-request), [when new tabs become available](https://playwright.dev/python/docs/api/class-browsercontext#browser-context-on-page).

At the first interference signal in any tab, mark the whole trial as stopping and record the time, tab, action, and request ID. Stop opening items, switching tabs, returning, and scrolling. A signal during the last viewing period still belongs to the trial. Requests already underway may finish; label activity after the signal and exclude it from counts taken at the stopping time. Close all tabs after saving the evidence. Do not retry blocked requests, solve challenges, or keep checking automatically for restored access. Measuring how long a block or challenge lasts is later work.

### What a “request” means

Keep three distinct counts:

1. **Item-opening attempts and successes:** one thumbnail-opening action is one attempt, whether it uses a new tab or the current one. Record when the content is ready, whether viewing in the selected tab finished, and any challenge, denial, error, or unfinished attempt. A completed view means the planned viewing duration finished without interruption; record separately whether scrolling reached the bottom of the page. Switching to an existing tab, scrolling it, or returning to the overview is not another item opening.
2. **BDR page requests:** count the HTML document requests for the initial collection, items, and overview returns, including additional requests caused by redirects. A redirect sends the browser to another URL. Count each request when it actually starts; a return action does not always require another page request.
3. **All BDR HTTP requests observed in the browser:** count page documents plus scripts, images, data requests, and other supporting content from the included hostnames across all tabs. Break counts down by hostname, kind of content requested, tab, whether the tab shows an overview or item, and workflow stage at request start. Report requests to other websites separately. Record the originating tab as well as the current stage, because an earlier tab may still load while another is being opened or reviewed.

Give each request an internal ID and link its response or failure to that ID. Do not count a request and its response as two requests. Redirects can generate more requests, and HTTP error responses do not necessarily produce Playwright's `requestfailed` notification. [Playwright request lifecycle](https://playwright.dev/python/docs/api/class-request).

These counts describe what the browser observed; they are not guaranteed to match Cloudflare's counters. Cached content, service workers (website code that can handle requests in the browser), other people sharing the public IP address, and Cloudflare's counting rules can create differences. Keep normal browser behavior and ask Central IT to match the evidence to the rule, action, and logs for the affected requests. Ray IDs help, but a sampled Security Events view may show only some requests. A request missing from that view may still have happened. [Playwright network behavior](https://playwright.dev/python/docs/network), [Cloudflare counting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/parameters/), [Ray ID lookup](https://developers.cloudflare.com/fundamentals/reference/cloudflare-ray-id/).

### The four requested time windows

Start measuring elapsed time at the first BDR collection request. Record opening, review, and return stages separately, and keep observing through the final view or return required by the workflow. At the first interference signal, or when observation ends without one, count requests across all tabs in the preceding **30, 60, 120, and 300 seconds**. Include the affected request if it started within that period.

For the precise calculation, let `W` be the window length and `t` the elapsed time when measurement ends. Count request starts in `(t - W, t]` when `t >= W`; if the available history is shorter, use `[0, t]`. Totals measured from the start of the run include the initial event at elapsed zero. Record the affected request's start and the later detection time separately. For item-attempt counts, use the opening-action start times. Among those attempts, count an item as successful only if its content was observed ready by the measurement end time. Keep unfinished attempts separate, and do not report an opened but unreviewed tab as a completed view.

For each window, show how much time was actually observed, item attempts/successes, page requests, all BDR requests, and the result when measurement stopped. A block 42 seconds after the run starts provides the full preceding 30 seconds but only 42 seconds of history for longer windows. Label those longer rows **partial observation**; do not estimate what the counts would have been over one, two, or five minutes.

Also show totals from the start of the run at the 30-, 60-, 120-, and 300-second marks that were reached. These answer “what happened during the first N seconds?” Times not reached are unavailable, not zero. A completed run without a block says “no interference observed within these limits”; it does not establish a maximum browsing rate that always works. Calculate counts afterward from saved events, without extra requests.

Suggested report wording, using placeholders rather than invented measurements:

> On `<local Eastern date/time with offset>`, with user-supplied Cloudflare settings `<label>` and workflow `<tabs/return>`, the trial first observed `<challenge/denial>` after `<elapsed>` seconds during `<workflow step>` in tab `<ID>`. Requested timing: `<time between openings and variation, if applicable; viewing duration and variation>`. Actual average and range of time between openings: `<values>`. In the preceding 30 seconds, the browser attempted `<N>` item openings and observed `<M>` BDR HTTP requests across all tabs, including `<D>` page requests. Evidence: `<status, kind of request, Ray ID>`. Confirmation of whether Cloudflare caused this: `<pending/confirmed>`.

Include comparable rows for 60, 120, and 300 seconds, stating how much of each period was observed. Avoid the unqualified statement “Cloudflare blocks at N requests.”

## Background: two ways to change IP addresses

These options were included at the maintainer's request for an overview and remain here as background for a separate investigation. Implementing either approach, including the software that changes IP addresses, is outside this Playwright CLI plan. They are not development tasks or later phases of this application.

Both approaches change the internet connection used by the browser so BDR can see a different public IP address. After a trial ends, the person running trials uses separate tools to choose the new connection and verify the address it presents, then starts the CLI again for a new trial and browser session. Starting another browser session or Docker container alone does not change the public IP address.

### 1. Choose a VPN or proxy connection with a known public IP address — recommended

A separately managed setup could provide a small set of VPN or proxy connections supplied by Central IT or an approved setup, each with a known public IP address. The person running trials chooses a connection with a different address between trials. VPN and proxy services are managed outside the app; the app's optional proxy setting lets the browser use an existing proxy. Playwright supports HTTP and SOCKS proxy settings. [Playwright proxy support](https://playwright.dev/python/docs/network#http-proxy).

For useful comparisons, the person preparing connections needs to verify that they provide different public IP addresses, keep the chosen connection unchanged during a trial, and confirm that it is connected. Check and record the chosen connection and observed address outside the CLI before the trial, without extra BDR requests. When checking a browser proxy's public IP address, make the check through that browser and proxy; a terminal command using the computer's normal connection might show another address. Central IT's BDR request logs provide stronger confirmation of the address BDR actually saw. If the proxy fails during a trial, the CLI ends the trial instead of switching automatically to a direct connection.

This approach gives more control over connection type, location, and repeated use. It requires access to several public IP addresses, whose previous use may still affect results. Several connections can share one public IP address, and reconnecting a VPN does not prove the address changed. Keep the protection being tested enabled, and record any existing exception for the chosen address.

Connection management remains outside the Python app. Its optional proxy server address stays fixed for the whole trial; separate tools handle connection changes between trials.

### 2. Use Tor through a separate program or container

In this approach, Tor runs separately and the Playwright browser uses Tor's existing SOCKS proxy. Between completed trials, a separate tool can authenticate to Tor and ask it to choose fresh paths through the Tor network for new requests; the person running trials can then start the CLI for another trial. An independently developed Docker setup could run the browser and Tor in separate containers. That setup is also outside this plan. Docker packages and runs the programs; Tor is what can change the public IP address BDR sees.

Tor's `NEWNYM` command requests fresh paths for new application requests, but Tor may limit how often it accepts the command. It does not guarantee a previously unused public IP address. Existing connections are not automatically moved, and the resulting public IP address must be checked. [Tor control specification](https://spec.torproject.org/control-spec/commands.html#signal).

Tor is inexpensive to explore, but makes comparisons harder to interpret. Its public IP addresses may already be blocked, and changing addresses introduces different recent traffic and network conditions. Tor documents that websites can recognize and block Tor traffic. Use it for trials explicitly labeled as using Tor, rather than the starting point for studying typical researcher access. [Tor website-blocking guidance](https://support.torproject.org/tor-browser/general/website-blocking-tor-exits/).

Tor may change the public IP address during a run or use different paths for different websites. An IP-check website alone cannot prove which address BDR saw throughout a trial. Match the trial to BDR's request logs when available. Otherwise, state that the address may have changed and do not treat the result as a measurement made under one verified public IP address. Using Playwright through Tor also does not give it all of Tor Browser's privacy settings. Selecting Tor paths, choosing new addresses, and coordinating Docker containers all belong to the separate work outside this CLI plan.
